\begin{abstract}
Virtual mentors for novice programmers need a reliable decision layer before they generate feedback. This paper studies that layer as a feedback-state classification problem within SocratesAI, a prototype that combines a Spring Boot backend, a FastAPI inference service, and interaction logging for later evaluation. A public dataset of Python Codeforces submissions is filtered to beginner-level problems and official judge outcomes are mapped to five mentor states: accepted, semantic debug, execution safety, efficiency review, and syntax repair. The main diagnostic benchmark contains 178,414 submissions from 872 problems after beginner-level filtering and class balancing. The source-code model, which uses hashed character n-grams, reaches a macro F1 of 0.426 compared with 0.085 for the majority baseline. After run-result summaries are included, the post-execution macro F1 reaches 0.814. To check whether this result depends on the selected split, we additionally ran a three-split grouped evaluation and a split-first experiment with an uncapped test partition. The model ordering remained the same in both experiments. The contribution is an explicit feedback-state formulation and a deployable decision layer for SocratesAI rather than a claim of classroom learning gains. The results indicate that source code is useful for early estimates, while execution signals are most useful as post-execution refinement evidence.
\end{abstract}

\section{Introduction}

Introductory programming is often difficult for beginners because they have to deal with several things at once: syntax, algorithmic reasoning, debugging, and testing. Because of this, student submissions can fail for very different reasons. Some contain syntax errors, others produce unsafe execution, incorrect logic, or solutions that are too inefficient. Judge output helps identify that something went wrong, but it does not always show what kind of feedback the student actually needs. A syntax error, for example, usually requires help with a specific part of the code. A time-limit error is more related to the efficiency of the chosen algorithm. For a wrong answer, it is often more useful to focus on edge cases or on the difference between the expected and actual output.

Many recent systems in programming education use large language models (LLMs) to generate explanations and hints \cite{Denny2024,Ahamed2025,CodeAid2024,Iris2024}. This is useful, but there is still an important step that comes before generating the feedback. The system first needs to understand what kind of help is suitable for the student's current state. If this decision is incorrect, even a well-written explanation may focus on the wrong problem and lead the student in the wrong direction.

This paper focuses on this decision layer. Instead of building a complete tutoring system, we study whether a machine learning model can predict an appropriate feedback state from the student's source code and, when available, from the results of code execution. The experiments are implemented within SocratesAI, a prototype that uses a Java Spring Boot backend together with a Python FastAPI ML service. The backend sends the student's submission for feedback-state prediction and then uses the predicted action to guide the feedback generation process. The predicted state and its confidence score are also stored in \texttt{interaction\_logs} for later analysis.

The paper addresses the following research questions:
\begin{itemize}
    \item \textbf{RQ1.} Can a learned feedback-state model generalize to submissions from beginner-level problems that were not used during training?
    \item \textbf{RQ2.} How much does prediction quality improve when source code is combined with run results such as passed tests, time, and memory?
    \item \textbf{RQ3.} Which feedback states remain unreliable, and how should SocratesAI handle low-confidence predictions?
\end{itemize}

The contribution of the paper is threefold:
\begin{itemize}
    \item it defines an operational feedback-state taxonomy that maps Codeforces judge outcomes to mentor decisions before free-form hint generation;
    \item it evaluates this decision layer on 178414 real Python submissions using a problem-level holdout that keeps unseen programming tasks out of training;
    \item it connects the trained model to SocratesAI through a confidence-aware inference path and structured interaction logging.
\end{itemize}
The novelty therefore lies in the feedback-state formulation and system integration, not in proposing a new classifier architecture.


\section{Related Work}

Automated support for programming exercises covers many feedback mechanisms. Keuning et al. review automated feedback generation for programming exercises, while the more recent surveys by Messer et al. and Kumar et al. show how broad the design space has become, including test-based feedback, repair-oriented feedback, and adaptive explanation systems \cite{Keuning2019,Messer2024,Kumar2025}. In this area, Wang et al. introduced SARFGEN, a data-driven system that generates repair-oriented feedback for introductory programming tasks using previous student solutions \cite{Wang2018}. This work shows that useful programming feedback can be automated. However, the main focus is still on generating or repairing feedback after the system has already identified the problem in the student's submission.

Another line of work emphasizes diagnosing the kind of error a student faces. Becker et al. study compiler-error enhancement for novice programmers, showing the value of improving how low-level failures are presented \cite{Becker2016}. Lobanov et al. classify recurring error types in programming-assignment submissions from an online learning platform \cite{Lobanov2019}. This diagnostic perspective is close to the present paper: before producing pedagogical language, the system should estimate which failure mode is most plausible from observable evidence.

This issue becomes even more important with LLM-based assistants. Denny et al. discuss desirable properties of AI teaching assistants in programming education, including reliability and alignment with learning goals \cite{Denny2024}. CodeAid reports a real classroom deployment of an LLM-based programming assistant \cite{CodeAid2024}, Iris explores an AI-driven tutor for computer science education \cite{Iris2024}, Liu et al. describe how human feedback was used to improve the CS50 AI assistant \cite{Liu2025}, and Ahmed et al. study AI-augmented feedback for CS1 \cite{Ahamed2025}. Sheese et al. further show that LLM tools change student help-seeking behaviour \cite{Sheese2024}, while Marwan et al. show the value of adaptive immediate feedback tied to learner state \cite{Marwan2022}. The present paper differs from those studies by focusing on the intermediate decision layer: it does not claim a full tutoring system or automatic program repair system, but tests whether a compact feedback-state classifier can decide the pedagogical direction before hint generation.

\section{Method}

\subsection{Feedback-State Formulation}

Let
\[
D=\{(x_i,y_i,g_i)\}_{i=1}^{n}
\]
be a dataset of programming submissions. Here $x_i$ is the observable submission information, $y_i$ is the feedback state, and $g_i$ is the problem identifier. The feature vector is
\[
x_i=(c_i,m_i,e_i),
\]
where $c_i$ is source code, $m_i$ contains problem and static-code metadata, and $e_i$ contains optional run-result signals.

The feedback state is a compact class describing the type of intervention needed by the mentor. In this paper,
\[
\begin{aligned}
Y=\{&\text{accepted},\text{semantic debug},\text{execution safety},\\
&\text{efficiency review},\text{syntax repair}\}.
\end{aligned}
\]
The states are derived from official judge outcomes. The exact mapping used before filtering and training is shown in Table~\ref{tab:outcomemap}. For example, a wrong answer is treated as a semantic-debug need, a time limit failure as efficiency review, a runtime or memory failure as execution safety, and a compilation error as syntax repair. This mapping is not a teacher-written hint. It is an operational target for the decision layer; the mentoring interpretation is summarized in Table~\ref{tab:taxonomy}.

A classifier estimates
\[
\hat{y}_i=f(\phi(x_i)),
\]
where $\phi(\cdot)$ is a feature representation. For the linear models used here, each class has a score
\[
s_k(x_i)=w_k^\top \phi(x_i)+b_k.
\]
The parameters are fitted by regularized logarithmic loss:
\[
\min_{W,b}-\sum_{i=1}^{n}\log P(y_i\mid \phi(x_i);W,b)
+\lambda\sum_{k}\|w_k\|_2^2.
\]
Problems are separated between training and testing:
\[
G_{\mathrm{train}}\cap G_{\mathrm{test}}=\varnothing.
\]
This split is stricter than a random row split because it tests whether the model works on new tasks, not only on new submissions to already seen tasks.

\subsection{Dataset and Features}

The empirical source is a local copy of the Codeforces Python submissions dataset \cite{MatrixStudio2026}. It was selected because it fixes the programming language family, contains accepted and failed submissions, provides official judge outcomes, and includes run-result fields such as passed tests, time, and memory.

The original dataset contains 690,396 Python submissions. After limiting the data to beginner-level problems with a rating of 1200 or lower and removing verdicts that do not belong to the defined taxonomy, 490,357 submissions from 881 problems remain. At this stage, the dataset is strongly dominated by the two largest classes, accepted and semantic debug. Together, they contain 411,943 submissions, which corresponds to 84.0\% of all filtered rows. To reduce this imbalance without removing examples from minority classes, the training script limits each class to at most 50,000 submissions. In practice, this cap affects only the accepted and semantic debug classes. After applying it, the final modeled dataset contains 178,414 submissions from 872 problems, while the share of the two largest classes decreases to 56.0\%. This step is used only to control class imbalance during macro-$F_1$-oriented training and should not be interpreted as the real distribution of student errors in a classroom.

The source code of each submission is represented using hashed character $3$--$5$-grams. This representation works well for program code because even short character sequences can capture useful patterns such as operators, indentation, brackets, delimiters, and identifier structure. At the same time, it does not require exact variable names to be shared between different solutions.

Several static features are also extracted from every submission, these include the number of lines, source-code length, blank lines, comments, average and maximum line length, branches, loops, functions, classes, imports, input calls, print calls, and exception-handling constructs. These features provide additional information about the structure and overall complexity of the submitted program.

The model also receives information about the programming problem itself, including the problem rating, its tags, and the Python version used for the submission. For the code-and-run setting, we additionally include execution-related features such as the number of passed tests, execution time in milliseconds, and memory usage in bytes. Importantly, the verdict itself is not provided to the model as an input feature. Instead, the execution-enriched model uses only derived information from the run results, avoiding direct use of the label from which the proxy mentor state is created.

The main classifier used in this study is Scikit-learn's \texttt{SGDClassifier} with logarithmic loss and $L_2$ regularization \cite{Pedregosa2011}. It was selected because the resulting feature vectors are sparse and high-dimensional. A linear model trained with stochastic gradient descent is a practical choice for this setting: it is relatively fast to train, easy to rerun under fixed experimental settings, and can be serialized and used directly by the Python service in SocratesAI.

At this stage, the goal is to understand how much mentoring signal can already be extracted from code fragments, static metrics, problem context, and execution results before moving to heavier neural models. The main comparison therefore varies the available evidence under one fixed linear classifier family rather than searching exhaustively over model families.

\section{Experimental Results}

Five models are compared: a majority baseline, a context-metrics model, a source-code model, a source-context model, and a code-and-run model. The reported metrics are accuracy, balanced accuracy, macro $F_1$, and weighted $F_1$. Macro $F_1$ is the main metric because the mentor should not be evaluated only on the largest classes.

Table~\ref{tab:results} reports the class-balanced diagnostic benchmark. The purpose of this comparison is to isolate which evidence sources improve the decision layer under one fixed linear classifier family, not to claim that SGD is the best possible classifier family.

\textbf{Baseline comparison.} The majority baseline is intentionally weak, but it is still informative: on the 42662-submission test split it collapses every case into semantic debug, classifies only 11589 submissions correctly, and yields macro $F_1=0.085$. The context-metrics baseline is stronger, reaching macro $F_1=0.310$, yet it still performs very poorly on execution safety ($F_1=0.078$). Adding raw source text is the first step that makes every feedback state meaningfully learnable. The source-code model improves macro $F_1$ by 0.116 over context metrics and by 0.341 over the majority baseline, with the clearest gains on syntax repair ($F_1=0.549$) and efficiency review ($F_1=0.440$). The source+context variant does not improve over source code alone on this split, so the paper does not claim that simple metadata and static counts consistently add value once character n-grams are already available.

The strongest result is obtained when run results are added. The code-and-run model reaches macro $F_1=0.814$ and balanced accuracy $0.821$. This model should be read as an evidence upper bound for the moment after execution evidence is available, not as a replacement for the source-only path that SocratesAI can use while the student is still editing. The supported conclusion is therefore narrower than saying that judge output solves mentoring: if SocratesAI has test-run evidence, it should treat that evidence as a central modelling signal, not only as a final grade.

Because the target taxonomy is itself derived from final Codeforces verdicts, a direct rule mapping from the final verdict token to the same labels would be perfect by construction and is therefore not a meaningful ML baseline. The code-and-run result should instead be interpreted more narrowly: it estimates the feedback state from derived run summaries such as passed tests, time, and memory, without seeing the verdict token itself. In SocratesAI, that corresponds to post-execution refinement when the mentor has execution telemetry but still needs to choose a pedagogical action.

\textbf{Additional classifier baselines.} A follow-up classifier-family comparison reused the same source-code signal but projected it to 128 SVD components so that all four shallow classifier families could train on the same representation. On that compressed space, linear SVM achieved the best macro $F_1$ at $0.383$, followed by SGD at $0.378$, Logistic Regression at $0.365$, and Random Forest at $0.358$. All four compressed-representation models remain below the main full-sparse source-code model ($0.426$ macro $F_1$), which suggests that preserving the high-dimensional character $n$-gram space matters more here than switching among these classifier families. For deployment, this supports keeping the sparse linear model used by the FastAPI service.

\textbf{Statistical validation.} The held-out test partition contains 42,662 submissions, providing reasonably precise accuracy estimates. The corresponding 95\% Wilson confidence intervals are $0.2674$--$0.2759$ for the majority baseline, $0.3297$--$0.3387$ for context metrics, $0.4004$--$0.4098$ for source code, $0.3992$--$0.4085$ for source + context, and $0.7769$--$0.7847$ for code + run. We also repeated the grouped evaluation with seeds 42, 52, and 62 to check whether the model ranking was caused by a particularly favorable split. The same general ordering was observed in all three runs. The majority baseline achieved macro $F_1=0.087 \pm 0.001$, followed by context metrics with $0.302 \pm 0.025$, source code with $0.420 \pm 0.005$, source + context with $0.399 \pm 0.011$, and code + run with $0.808 \pm 0.007$. These results suggest that the relative performance of the models remains stable across the tested unseen-problem splits rather than depending on a single favorable partition.

\textbf{Split-first follow-up.} The main balanced benchmark applies class capping before the train-test split, so we also performed an additional experiment with a cleaner sequence. In this setup, the data is first split by problem, the class cap is applied only to the training partition, and the test partition remains unchanged. The resulting test set contains 118,310 submissions and therefore follows a more natural class distribution. The overall ordering remains the same: majority macro $F_1=0.139$, context metrics $0.224$, source + context $0.319$, source code $0.349$, and code + run $0.798$. The absolute macro-$F_1$ values are lower because accepted and semantic-debug submissions dominate the uncapped test set, but the relative ordering of the different evidence sources does not change.

RQ3 also concerns how SocratesAI should handle low-confidence predictions. On held-out source-code predictions, requiring confidence of at least 0.35 retains 58.1\% of submissions and raises macro $F_1$ to $0.493$. Raising the threshold to 0.50 retains 11.5\% of submissions with macro $F_1=0.608$, and raising it to 0.70 retains 2.9\% with macro $F_1=0.748$. The current prototype therefore uses 0.35 as a pragmatic operating point: it improves reliability over unrestricted source-only prediction without collapsing coverage to a tiny minority of cases.

\section{Integration into SocratesAI}

The trained model is placed between code analysis and feedback generation layers in SocratesAI. In the current prototype, a Java 21 Spring Boot backend collects analyzer output, session context, and the student's source code, serializes those fields as JSON, and calls the FastAPI endpoint \texttt{/predict-mentor-state}. The Python ML service reconstructs the same source metrics used during training, applies the fitted pipeline, and returns a response that includes the predicted mentor state, confidence score, per-class scores, and a mapped feedback action.

The Spring Boot backend uses that action for bounded feedback generation and stores the returned mentor state and confidence in \texttt{interaction\_logs}. When ML mode is enabled but confidence is below the current operating threshold of 0.35, the backend keeps the ML prediction for logging but falls back to the rule selector for the final action. This design keeps the prediction connected to the product without allowing an uncertain prediction to drive the intervention.

The implementation has two modes: source-only mode, in which the mentor can make an early estimate while the student is still editing, and code-and-run mode, in which test execution evidence is also available and the prediction becomes much more reliable. This aligns with a realistic CS1 workflow: a student writes code, runs or submits it, and receives a short intervention tied to the observed failure type.

The main purpose of this trained model is to select the pedagogical direction instead of providing the final answer. For example, a high-confidence efficiency-review prediction can lead to a prompt about time complexity, while a low-confidence semantic-debug prediction can trigger a more cautious leading question about expected versus actual output. In the current prototype, LLMs are used only to phrase the selected action in natural language. The prompt is bounded so that it does not provide a full solution, rewrite the student's program, or ignore the predicted feedback state. The repository also stores post-hoc outcomes such as \texttt{feedback\_helpful}, \texttt{feedback\_rating}, \texttt{resolved\_after\_feedback}, and expert labels, which makes later classroom or expert validation possible even though those data are not the main evaluation source in the present paper.

\section{Discussion and Limitations}

The results show that a machine learning model can learn meaningful feedback-state signals from real programming submissions, but source code alone is not enough for reliable tutoring on unseen problems. Run results change the problem substantially. This is not a weakness of the experiment; it is a design lesson for SocratesAI. A mentor that ignores passed tests, time, and memory discards evidence that helps separate failure modes.

Several limitations bound this conclusion. First, the labels are proxy mentor states derived from Codeforces verdicts, not teacher-written pedagogical annotations. Second, the code-and-run benchmark should be interpreted as a post-execution upper bound, not as evidence that ML is needed once a platform already exposes the final verdict token directly. Third, the main ablation table uses a balanced benchmark, although both the additional three-split rerun and the split-first follow-up preserve the same ordering across unseen-problem partitions. Fourth, although SocratesAI now logs mentor-state predictions, usefulness ratings, resolution flags, and expert labels, those interaction logs are not yet large enough to serve as the main quantitative evaluation dataset. Finally, beginner-rated Codeforces problems differ from real CS1 tasks that may also emphasize style, decomposition, and explanation quality.

These limitations are acceptable only within the scope claimed here: the paper presents a feasible ML decision layer for a virtual mentor, not a finished educational product and not evidence of learning gains. The next research step is to keep collecting SocratesAI interaction logs and validate the model on target-domain student data.

\section{Conclusion}

This paper presents the feedback-state decision layer of a virtual programming mentor as a supervised machine learning task. Using real Python submissions from beginner-level Codeforces problems, the study shows that source-code features provide useful early signals, but they are still not enough when the model is tested on unseen problems. On the main balanced benchmark, the source-code model achieves macro $F_1=0.426$, while the code-and-run model achieves macro $F_1=0.814$. A split-first follow-up with an uncapped test partition preserves the same ordering, although with lower absolute macro-$F_1$ values under the natural class skew.

The main supported conclusion is pragmatic: a virtual mentor should not rely only on generated explanations or on the submitted source code, but should estimate an appropriate feedback state, use execution results when they are available, and store predictions and outcomes inside the application for later validation. In SocratesAI, this connects the external Codeforces study to the deployed prototype: the ML service predicts the feedback state, the feedback layer turns it into a bounded hint, and \texttt{interaction\_logs} form the basis for future classroom evaluation. Stronger claims about educational effectiveness still require real classroom evidence.
