# Локальная демонстрация без покупки хостинга

Стенд запускает настоящий интерфейс, Spring Boot API, PostgreSQL, авторизацию, WebSocket-ментор и фоновые задания. **Проверка решений имитируется** отдельным закрытым HTTP-сервисом: он узнаёт три точных примера и возвращает синтетические результаты. Он не запускает Python, Java или C++ и не компилирует присланные программы. Время и память в вердиктах также синтетические. На каждой странице есть предупреждение об этом.

Это демонстрация пользовательских сценариев. Для проверки произвольных решений потребуется отдельная изолированная песочница Judge0. Для публичного размещения потребуются хостинг, домен и TLS; этот HTTP-стенд доступен только с текущего компьютера.

## Запуск

Нужны работающий Docker, Docker Compose **2.24.4+**, Bash и Python 3. Команды выполняются из корня репозитория. Java/Node/Python-зависимости приложения собираются внутри образов. Первый запуск может занять несколько минут и требует интернета для загрузки базовых образов и зависимостей.

```bash
bash scripts/demo/demo.sh up
```

Откройте **http://localhost:8088** в браузере. Если этот порт занят, остановите занимающий его процесс; скрипты и browser-тест намеренно используют один фиксированный адрес.

Скрипт автоматически создаёт демонстрационные аккаунты, выдаёт преподавателю роль через административный API, публикует задачу и коллекцию после синтетической проверки эталонов на трёх языках. Отдельный технический аккаунт проверяет Run/Submit/прогресс, оставляя аккаунт `student` для вашей первой попытки.

Пароли и готовые примеры программ находятся в **`.delivery/demo/access.md`**. Откройте файл в IDE. Он создаётся локально, доступен только владельцу и исключён из Git и образов. Пароли случайные; общего пароля в коде нет. Не удаляйте `.delivery/demo/`, пока сохраняете том этой демонстрационной БД: там находятся соответствующие ей учётные данные.

## Что показать

1. Войдите под `student` из локального файла, откройте задачу «ДЕМО · Сумма двух чисел».
2. Выберите `python3`, введите `print(0)` и нажмите **Run samples**: появится `WRONG_ANSWER`.
3. Скопируйте **весь** пример Python из `access.md`, нажмите **Run samples**, дождитесь `ACCEPTED`.
4. Нажмите **Submit** и дождитесь результата. Проверьте **Profile**: задача получила статус `Solved`. Для скрытого теста показываются только вердикт и метрики.
5. Выберите Java или C++ и используйте соответствующий точный пример из файла. Переключение языков сохраняет буферы в памяти. Произвольно переписанные решения в этом стенде не проверяются по смыслу и получат `WRONG_ANSWER`.
6. При редактировании дождитесь статуса `connected` и ответа ментора либо нажмите **Ask mentor**. В актуальном native-контуре подсказки пишет Gemini, а ML классифицирует Python. В локальном демо LLM-провайдеры выключены: будет явное сообщение о недоступности AI; вымышленные RULE-подсказки не подставляются. Реальные AI-подсказки проверены отдельно в production.
7. Выйдите и войдите под `teacher`: **Teaching** показывает задачу и коллекцию; можно редактировать черновики и смотреть тесты. Синтетическая верификация принимает только документированные примеры и вход из двух целых чисел. Аккаунт `admin` имеет экран **Roles**.

## Остановка и повторный запуск

```bash
bash scripts/demo/demo.sh status
bash scripts/demo/demo.sh down
bash scripts/demo/demo.sh up
```

`down` сохраняет данные в именованном томе `socrates-local-demo_postgres_data`. Повторный `up` сохраняет аккаунты и прогресс. Не применяйте `down -v`. Проект всегда называется `socrates-local-demo`, использует собственную БД `socrates_demo` и не подключается к базам 21/22 или к `.env` разработчика.

Если меняли приложение, пересоберите соответствующий образ перед `up`, например:

```bash
docker build -t socratesai/frontend:delivery-test socratesai-frontend
bash scripts/demo/demo.sh up
```

Проверьте Docker при ошибке запуска. Сообщение «port is already allocated» означает занятый 8088. При ошибке сборки проверьте доступ к реестру образов/Maven/npm. Не публикуйте содержимое `compose.env`, `access.json` или полный вывод `docker inspect`/`docker compose config`: там могут быть секреты. Для валидации Compose используйте только `config --quiet`.

## Повторяемые проверки

Без запущенного приложения можно проверить поведение имитатора:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests/demo
```

Для browser-теста нужен запущенный стенд и Node 22. Тест использует реальные UI/API/WS, создаёт отдельного учебного студента и не подменяет запросы браузера:

```bash
cd socratesai-frontend
npm ci
npx playwright install chromium
PLAYWRIGHT_CHANNEL=chromium npm run demo:e2e
```

После теста скриншот рабочего пространства находится в `.delivery/demo/workspace.png`. Трассировки и видео выключены, логины/пароли не публикуются.

Из корня можно проверить аварийный перезапуск **только этого локального backend-контейнера**. Не запускайте параллельно с browser-тестом или ручной проверкой:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 scripts/demo/recovery.py
```

Скрипт отправляет задержанный синтетический пример от технического аккаунта, дожидается `RUNNING`, завершает демо-бэкенд сигналом KILL и проверяет восстановление по lease с увеличением generation. Номер попытки студента сохраняется, повторного POST-батча к имитатору нет. Несекретные результаты записываются в `.delivery/demo/recovery.json`. Это не проверка реального Judge0 или отказоустойчивости продакшена. Сам имитатор хранит токены в памяти: его перезапуск во время проверки может дать `SYSTEM_ERROR`; запустите новую попытку.

## Изоляция

Публикуется только `127.0.0.1:8088`; БД, ML и имитатор не имеют host-портов. Используются ограничения памяти/CPU/PID, non-root пользователи, read-only rootfs и отдельный том PostgreSQL. Локальная роль приложения не является суперпользователем. Секреты генерируются через CSPRNG операционной системы и передаются через окружение контейнеров. Демонстрационный каталог с вымышленными language IDs и Compose overlay не включены в production build contexts и не должны использоваться для публичного размещения.
